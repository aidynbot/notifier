# Требования к MVP

## Назначение

MVP демонстрирует создание процессуального уведомления специалистом, его отправку в демо-кабинет предпринимателя, SMS-оповещение через внешний шлюз и фиксацию истории обработки. Демо-кабинет имитирует личный кабинет бизнеса в сценарии, похожем на eGov Business.

Интеграция с 1414 не используется. Подписание ЭЦП и формирование документа с QR-кодом запланированы после MVP.

## Роли и доступ

### Специалист

- Создаёт уведомления и просматривает свои уведомления и их историю.
- Выбирает одну или несколько статей из справочника.
- Если статьи нет в справочнике, указывает её реквизиты вручную.
- Если для выбранной статьи отсутствует шаблон, включает checkbox для ввода текста вручную. Для каждой статьи без шаблона текст вводится отдельно.
- Может изменить предложенный адрес явки для текущего уведомления.
- Может сохранить изменённый адрес как свой адрес по умолчанию отдельной кнопкой.

### Предприниматель

- Просматривает доставленные ему уведомления в демо-кабинете.
- Открытие уведомления фиксируется как прочтение.

### Руководитель

- Просматривает все уведомления и истории специалистов.

### Администратор

- Имеет полный доступ к системе.
- Управляет пользователями.
- Добавляет и редактирует статьи и шаблоны.
- Просматривает системные логи действий: кто и когда входил, какие действия выполнял, а также ошибки интеграций.

## Справочник статей и тексты

- Статья выбирается как полная позиция справочника, например «190, часть 5, пункт 3».
- Кнопка «+» позволяет добавить к уведомлению ещё одну позицию.
- Если статьи нет в справочнике, специалист вручную указывает её реквизиты и текст. Такая запись должна быть видна администратору для последующего добавления статьи и шаблона в справочник.
- Если шаблон статьи есть, система использует его текст.
- Если шаблона нет, специалист включает checkbox и вводит текст для этой статьи. Для нескольких статей без шаблонов текст указывается отдельно по каждой статье.
- Тексты выбранных статей объединяются в одно уведомление.
- При создании уведомления сохраняется снимок сформированного текста, чтобы последующие изменения шаблона не меняли уже созданное уведомление.

## Вложения

- Для статей в справочнике настраивается, требуется ли акт о назначении проверки и проверочный лист.
- Если хотя бы одна выбранная статья требует эти документы, оба файла обязательны для отправки.
- В этом случае форма показывает слоты для загрузки акта и проверочного листа.
- Если ни одна выбранная статья не требует документы, слоты не отображаются.
- Пример: для `8-1 + 190` файлы обязательны из-за `8-1`; для `190, часть 5` без других требующих статей — не нужны.

## Адрес и дата явки

- У каждого специалиста свой адрес явки по умолчанию (например, кабинет в конкретном здании).
- Адрес подставляется при создании уведомления, но специалист может изменить его для текущего уведомления.
- Новое значение становится адресом по умолчанию только если специалист нажмёт отдельную кнопку сохранения.
- Специалист указывает дату и время явки.

## Сценарий создания и отправки

1. Специалист вводит данные бизнеса (БИН, название и контактный номер), выбирает статью или несколько статей, дату и время явки.
2. Система формирует текст по шаблонам. Для статьи без шаблона специалист включает checkbox и вводит текст вручную; для отсутствующей в справочнике статьи также указывает её реквизиты.
3. Система определяет обязательность вложений по всем выбранным статьям и показывает нужные слоты. Если документы обязательны, без обоих файлов отправить уведомление нельзя.
4. Адрес подставляется из настроек специалиста; его можно изменить. Отдельная кнопка сохраняет новый адрес по умолчанию.
5. После заполнения открывается предпросмотр уведомления.
6. В предпросмотре есть кнопка «Редактировать», которая возвращает специалиста в ранее заполненную форму. После изменений специалист снова может открыть предпросмотр.
7. Из предпросмотра специалист нажимает кнопку отправки.
8. Система передаёт уведомление в демо-кабинет бизнеса и отправляет SMS через настроенный внешний шлюз (или имитирует отправку через mock-провайдер).
9. Предприниматель открывает уведомление в демо-кабинете; система фиксирует `READ` и время прочтения.

## История и аудит

- История уведомления показывает этапы создания, отправки в кабинет, результат SMS, прочтение и ошибки.
- Аудит записывает пользователя, время и действие, например вход в систему, создание/редактирование/отправку уведомления, изменение адреса и действия администратора.
- Аудит обеспечивает журналирование и разбор событий; он не сверяет целостность файлов.
- Проверка целостности файлов по SHA-256 хэшам — отдельная функция и может быть добавлена отдельно.

## Провайдеры и SMS

- Доставка в кабинет реализуется демо-провайдером с фиксацией статусов `DELIVERED` и `READ`.
- SMS реализуется через интерфейс провайдера, чтобы подключение или замена внешнего шлюза не меняли бизнес-логику.
- Для разработки и демонстрации без фактической отправки используется mock-провайдер.
- Реальные SMS отправляются через выбранный доступный внешний SMS-шлюз; 1414 исключён.
