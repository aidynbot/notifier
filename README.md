# GovTech: сервис уведомлений для бизнеса

Демо-сервис для подготовки и доставки процессуальных уведомлений субъектам предпринимательства. MVP показывает работу специалиста государственного органа и демонстрационного личного кабинета бизнеса в сценарии, похожем на eGov Business.

> Это демонстрационный проект: кабинет бизнеса и интеграции могут работать в тестовом режиме. SMS отправляются через выбранный внешний SMS-шлюз; интеграция с 1414 в MVP не используется.

## Цель MVP

Показать полный основной сценарий: специалист создаёт уведомление, система сохраняет его и передаёт в демо-кабинет бизнеса, затем отправляет SMS через внешний шлюз. В демо-кабинете можно открыть уведомление; система фиксирует статус доставки и факт прочтения.

## Функциональность MVP

- Создание уведомления с данными субъекта бизнеса (БИН, название, контактный номер), основанием, сроком и адресом явки.
- Просмотр списка уведомлений и карточки с историей статусов.
- Демонстрационная доставка в личный кабинет бизнеса со статусами `DELIVERED` и `READ`.
- Отправка SMS через внешний шлюз, кроме 1414. Результат отправки (успех или ошибка и идентификатор сообщения, если он предоставлен шлюзом) сохраняется для отображения в карточке.
- Аудит действий пользователей и системных событий.
- Конфигурация интеграции с SMS-шлюзом через переменные окружения; тестовый `MockSmsProvider` для демонстрации без реальной отправки.

## Архитектура и границы ответственности

- **API и сервис уведомлений** проверяют входные данные, создают уведомления и координируют доставку.
- **Демо-провайдер кабинета бизнеса** имитирует передачу уведомления и получение статусов доставки и прочтения.
- **SMS-провайдер** изолирует API конкретного внешнего шлюза. Замена шлюза не должна требовать изменения логики уведомлений.
- **Аудит** фиксирует, кто, когда и какое действие выполнил: например, создание уведомления, отправку в кабинет, отправку SMS, изменение статуса и ошибку интеграции. Аудит нужен для истории и разбора событий; сам по себе он не сверяет целостность файлов.
- **Проверка целостности** — отдельная функция: для файлов вычисляются SHA-256 хэши, а при последующей проверке содержимого хэш пересчитывается и сравнивается с сохранённым значением. Несовпадение означает, что файл изменился. В MVP эту функцию можно добавить вместе с загрузкой вложений и манифестом пакета.

## Технологический стек

- Python, FastAPI, Pydantic
- PostgreSQL, SQLAlchemy, Alembic
- Внешний SMS-шлюз через адаптер `SmsProvider`
- Демо-адаптер кабинета бизнеса через `DeliveryProvider`

## Переменные конфигурации SMS

Секреты и настройки реального шлюза хранятся вне исходного кода, например в `.env` (сам файл не коммитится):

```env
SMS_PROVIDER=mock
SMS_GATEWAY_BASE_URL=
SMS_GATEWAY_API_KEY=
SMS_SENDER=
```

Для реальной отправки значение `SMS_PROVIDER` выбирает адаптер подключённого внешнего шлюза. `mock` используется для локального демо и не отправляет сообщения. 1414 не является провайдером MVP.

## Сценарий демонстрации

1. Специалист создаёт уведомление и указывает данные бизнеса, основание, дату, время и адрес явки.
2. Система сохраняет уведомление и записывает событие в аудит.
3. Адаптер передаёт уведомление в демо-кабинет бизнеса; в истории появляется статус доставки.
4. SMS-адаптер отправляет сообщение через настроенный внешний шлюз либо имитирует отправку в режиме `mock`.
5. Пользователь открывает уведомление в демо-кабинете, после чего статус меняется на `READ`; это событие также попадает в аудит.

## Возможное развитие после MVP

- Загрузка обязательных вложений и правила комплектности по основаниям.
- SHA-256 хэши файлов и манифест пакета для проверки целостности.
- Подписание ЭЦП через NCALayer и серверная проверка подписи.
- Генерация PDF и публичная проверка документа по QR-коду.
- Ролевая модель и подключение реального кабинета бизнеса, если соответствующий официальный интерфейс будет доступен.
